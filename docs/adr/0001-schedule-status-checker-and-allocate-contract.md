# ADR 0001. Статусы расписания, независимый чекер и контракт `allocate_fn`

- Дата: 2026-10-15
- Статус: принято
- Связано: issue #1 (ядро и чекер, этап 1), `prior_work_overlap.md` п. 1.2, 1.5, 1.6

## Контекст

Версия каркаса `d3dadbc6` (коммиты 77187c3 + 224bf39) не гарантировала допустимость расписаний:
ресурсы списывались по выводу `allocate_fn`, а освобождались по `job.resources_required`;
тупик прерывал цикл, и makespan считался по неполному расписанию; невалидный `job_id`
подменялся молча; Case 1 решался без ресурсов (`resource_requirements` не читался),
Case 3 — без бюджета (`nonrenewable` ≠ `non-renewable`), Case 5 — с 92 работами вместо 184
(id работ двух проектов совпадали). Раннеры считали «OK» по отсутствию исключения,
а качество брали из вывода сгенерированного кода. Схема планирования не была SSGS:
старт только в текущий момент, готовность по завершённым, а не по запланированным
предшественникам, без вставки в более ранние окна.

## Решение

1. **Статусы вместо «запустилось».** `run_schedule` возвращает `status` (`complete` | `incomplete`),
   `reason` (`deadlock` | `infeasible` | `max_iterations`), `detail`, `unscheduled`, `skipped`,
   `invalid_select_count`, `allocate_violations`. При `incomplete` `objective["primary"] = None`.
   `strict=True` превращает любое нарушение в `SchedulerContractError`.
2. **Ресурсы бронирует каркас.** В обеих схемах бронируется не меньше `job.resources_required`,
   освобождается ровно то, что забронировано; вывод `allocate_fn` не может уменьшить потребление.
3. **Стандартная SSGS** (`scheme="ssgs"`, по умолчанию): готовы работы, у которых все
   предшественники запланированы; работа ставится в допустимое время по предшествованию и
   профилю ресурсов на всём интервале `[t, t + d)`, включая вставку раньше уже поставленных
   работ. Пошаговая схема сохранена как `scheme="legacy"` только для воспроизведения
   весенних результатов.
4. **Новый контракт `allocate_fn`:** `allocate_fn(job, feasible_starts, snapshot, meta) -> int`
   выбирает время старта из списка допустимых (по возрастанию, допустимость гарантирует каркас).
   Значение не из списка — `allocate_violations += 1`, берётся самое раннее. Старый контракт
   (`-> dict[int, int]`) работает только в `legacy`.
5. **Независимый чекер** `src/schedule_checker.py::validate_schedule(instance, schedule)`
   не импортирует каркас, проверяет полноту, предшествование, возобновляемые ресурсы по тактам,
   бюджеты невозобновляемых, группы выбора и пересчитывает цель по данным инстанса.
   Статусы: `valid` | `invalid` | `incomplete` | `empty`; `valid` не означает `optimal`.
   Ключ работы многопроектной задачи — `project_id * 10^k + local_id` (`k` — число цифр в
   максимальном локальном id), кортеж `(project_id, local_id)` или строка `"project_id:local_id"`.
6. **Единые раннеры** (`experiments/runners/runner_common.py`): статусы `generation_error`,
   `compile_error`, `runtime_error`, `timeout`, `no_schedule`, `infeasible`, `incomplete`, `ok`;
   один таймаут 30 с; доли от всех генераций; качество только из чекера.
   `no_schedule` добавлен к списку из постановки: вывод полного решателя, из которого
   расписание не извлекается, нельзя честно отнести ни к `runtime_error`, ни к `infeasible`.
7. **Строгая схема инстанса** в `ProblemFactory`: неизвестный тип ресурса, ссылка на неизвестный
   ресурс или работу, отрицательные значения — `InstanceFormatError`, а не ноль или пустое значение.
8. **Цель многопроектной задачи** — сумма makespan проектов (`total_makespan`, как в README);
   дополнительно отдаётся `portfolio_makespan` (максимум). В MPSPLIB «Total Makespan» — это
   максимум; какую величину считать основной, решить до этапа 3 и зафиксировать в DSL.
9. **Case 2:** директивный срок приведён к сырому файлу OR-Library (`sch50`, инстанс 1, `h = 0.2`):
   `Σp = 549`, `d = ⌊0.2 · 549⌋ = 109` вместо `106`. Весенние генерации Case 2 решали задачу
   с другим сроком.

## Последствия

- Весенние числа по Cases 1, 3, 5 не воспроизводятся новым ядром по построению
  (ресурсы, бюджет, число работ); перепрогон 150 запусков — этап 2.
- Cases 3–4 (данные 4TU с альтернативными подграфами) в обеих схемах приходят к тупику
  после выбора ветви: потомки пропущенных работ никогда не становятся готовыми. Так было и
  в `d3dadbc6` — тест на покрытие `0 < scheduled <= num_jobs` это скрывал. Семантика
  групп выбора (кто пропускается транзитивно, когда готов узел-слияние) в каркасе
  не определена; до решения эти постановки — `unsupported`, тесты закрепляют честный
  статус `incomplete`.
- Промпт skeleton-клиента и справка в `app.py` переписаны под новый контракт;
  функции весенних генераций (`allocate_fn -> dict`) исполняются только в `scheme="legacy"`.
