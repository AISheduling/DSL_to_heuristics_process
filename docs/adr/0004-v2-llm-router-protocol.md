# ADR 0004. Протокол эксперимента В2-LLM: маршрутизатор по метахарактеристике F1

- Дата: 2026-11-09
- Статус: принят 2026-11-09, до генерации; после первого вызова LLM меняется только
  новой записью в этом ADR
- Связано: ADR 0001 (ядро, чекер), ADR 0003 (протокол В1: промпт, генерация, прогон в
  каркасе), `experiments/v2_counterexamples/README.md` (сетка F1, критерии C1–C4, пороги),
  `src/generators/traps/resource_blind_slack.md` (ловушка F1)

## Контекст

На сетке `f1-grid` (2160 синтетических проектов, seed 0–19) ловушка F1 «ресурсно-слепой
резерв» подтверждена: если у ловушки свой ресурс (`isolated`), LST и MTS проигрывают
во всех 12 ячейках (C1–C4 выполнены, медиана проигрыша при s ≥ 0,5 — 10,3–11,9 п. п.;
`results/f1-grid/invariants.md`). При общем ресурсе (`shared`) проигрыш есть, но слабее
(C2 выполнен, C1, C3, C4 — нет). Метахарактеристика `f1_pressure_free` с порогом
0,0564 отделяет проигрыши LST: сбалансированная точность 0,79 на обучении (n = 30, 60),
0,99 на n = 120 `isolated`, 0,66 на n = 120 `shared` (`results/f1-grid/triggers.md`).

Созвон с научным руководителем 2026-11-09: проверить, помогает ли LLM знание о свойстве
проекта, через **маршрутизатор** — код до вызова LLM считает метахарактеристику,
сравнивает с порогом и по результату выбирает описание проекта. Два варианта описания,
без совмещения:

- **«вердикт»** — готовый вывод: LST и MTS здесь не брать;
- **«свойство»** — значение характеристики и что оно значит, без названий правил.

Если работает «свойство», это сильнее: модель сама выводит, какой класс правил не годится.
Если не работает — понадобится экспертное дерево решений, и интересно, насколько LLM от
него отстает.

Вопрос В2-LLM: на проектах, где маршрутизатор сработал, дает ли описание «вердикт» или
«свойство» эвристику с меньшим makespan, чем описание без метаданных?

## Решение

1. **Уровни** (сравниваются внутри одного запуска, как в В1).
   - **(б) без метаданных** — DSL состава `none`, как уровень (б) В1.
   - **(в) вердикт** — маршрутизатор; при срабатывании к DSL (б) добавляется блок
     `rule_guidance` (п. 3).
   - **(г) свойство** — маршрутизатор; при срабатывании к DSL (б) добавляется блок
     `project_properties` (п. 3).
   Уровень (а) В1 (12 индикаторов) не входит: он отвечает на другой вопрос, а на
   синтетике индикаторы guo2021 проигрыш LST не предсказывают (BA ≤ 0,58 на n = 120,
   `triggers.md`).

2. **Маршрутизатор** (модуль в `src/`, реализация — следующий шаг плана).
   - Считает `f1_pressure_free` (`src/rule_features.py`) по самому проекту и сравнивает с
     порогом из `experiments/v2_counterexamples/results/f1-grid/triggers.json`
     (правило LST: `f1_pressure_free > 0.05639177443290227`). Порог MTS тот же. Порог
     берется из файла как есть, ради результата не меняется.
   - Сработал — в DSL добавляется блок уровня; не сработал — DSL уровня (в) и (г) равен
     DSL (б).
   - Решения маршрутизатора для всей выборки считаются **до генерации** и пишутся в
     манифест запуска (проект → значение признака → сработал ли). Число вызовов LLM
     известно до запуска.

3. **Тексты блоков DSL.** Промпт В1 (`src/llm_clients/prompt_v1.py`, версия
   `v1-2026-10-27`) не меняется — различается только DSL, как в В1. Блоки идут в DSL
   после `optimization_objectives`; числа — три знака, как индикаторы.

   (в) вердикт:
   ```json
   "rule_guidance": {
     "avoid_rules": ["LST", "MTS"],
     "text": "На этом проекте правила приоритета LST (первой ставится работа с самым ранним поздним стартом) и MTS (первой ставится работа с наибольшим числом всех последующих работ) дают заметно худший makespan. Не используй их."
   }
   ```
   Только запрет, без подсказки, что брать вместо (руководитель: «LST здесь не брать и
   MTS тоже»). Расшифровка названий нужна, чтобы модель поняла, о каких правилах речь.

   (г) свойство:
   ```json
   "project_properties": {
     "f1_pressure_free": {
       "value": 0.123,
       "threshold": 0.056,
       "meaning": "В проекте есть пары работ h и c, не связанных предшествованием, которые не помещаются на ресурс одновременно. Работа c лежит на критическом пути. Поздние сроки расходятся: поздний старт c раньше, чем у h (LS_c < LS_h), а поздний срок окончания h раньше, чем у c (LF_h < LF_c), — за h идут работы, которых ждет критический путь. Если поставить c раньше h, h ждет конца c, работы после h опаздывают, и вместе с ними опаздывает критический путь. Значение — сумма таких возможных опозданий (с учетом свободного ресурса рядом с c), деленная на длину критического пути. Выше порога свойство выражено и заметно влияет на makespan."
     }
   }
   ```
   Названий правил нет. Описание использует понятия CPM (поздний старт, позднее
   окончание) — без них свойство не сформулировать; это ограничение уровня (г): он не
   «нейтрален к правилам» полностью, но вывода «какое правило брать» в нем нет.

   В DSL по-прежнему нет имени проекта, параметров генератора (окружение, s, seed) и
   эталонов. Блок `generator` проекта в DSL не попадает.

4. **Выборка** — синтетика F1, тот же генератор и параметры, что в `f1-grid`, но
   **новые seed 20–24**: порог подбирался на seed 0–19, и проверка на тех же проектах
   завысила бы точность маршрутизатора.
   - Сетка: окружение {`isolated`, `shared`} × n {30, 60} × s {0; 0,5; 1} × seed 20–24,
     n_res = 4, контроль `fits` — **60 проектов**.
   - n = 120 не берется ради стоимости; размер на эффект не влиял (`invariants.md`).
     n_res = 4 — как в PSPLIB; при 2 и 4 ресурсах проигрыш одного порядка.
   - s = 0 — контроль: на нем маршрутизатор не должен срабатывать, а если сработал —
     это ложная тревога, и видно, не портит ли подсказка обычный проект. В `shared` при
     s = 0 ложные тревоги ожидаются примерно в трети проектов (13/40 на `f1-grid`, п. 5).
   - PSPLIB в В2-LLM не входит: маршрутизатор сработал на 1 инстансе из 108
     (`triggers.md`), сравнивать не на чем.

5. **Генерация** — как в ADR 0003, п. 7: Haiku (`anthropic/claude-haiku-5-5`),
   `temperature` 0,7, `max_tokens` 16000, `PROXY_CACHE` в каждом запросе, 5 генераций на
   проект и уровень, файлы ответов по образцу В1.
   - **Повторное использование (б).** Где маршрутизатор не сработал, запрос (в) и (г)
     совпадает с (б) по построению. Такие генерации не запрашиваются заново: (в) и (г)
     получают генерации (б) этого проекта, в файле — `copied_from`. Это не подмена:
     политика «маршрутизатор + LLM» на этом проекте выдает ровно то же описание.
   - **Число вызовов**: 60 × 5 = 300 для (б) плюс 2 × 5 × (число сработавших проектов).
     Доля срабатываний на тех же ячейках `f1-grid` (n = 30, 60; n_res = 4; `fits`;
     seed 0–19; `features.csv`): `isolated` — s = 0: 0/40, s = 0,5: 35/40, s = 1: 39/40;
     `shared` — 13/40, 26/40, 36/40. Отсюда ожидается около 37 срабатываний из 60:
     **около 670 вызовов, ≈ $1,4**; верхняя граница при 60 срабатываниях — 900 вызовов,
     ≈ $1,9. Оценка — по
     `full-haiku-2`: перегенерация (б) 540 вызовов = $1,15 (ADR 0003, п. 7). Точное
     число — из манифеста (п. 2) до запуска.
   - Стоимость — фактическая разность Spend в LiteLLM; после запуска проверяются
     `fast_replies` и `repeated_replies`.

6. **Прогон в каркасе** — как в ADR 0003, п. 8: одно построение SSGS на генерацию,
   отдельный процесс, таймаут 30 с, makespan — из независимого чекера, статусы — из
   `runner_common.STATUSES`. На тех же проектах — правила RULES_V2 (LFT, LST, MTS, GRPW,
   GP1) и эталон.

7. **Эталон и метрика.**
   - Эталон — `best_known` (`src/reference_solver.py`, `samples = 100`, `seed` = seed
     проекта — как в `f1-grid`) и LB. Это эвристическая верхняя граница, а не оптимум
     (на `f1-grid` доказанный оптимум у 5,6 % проектов, медиана разрыва best/LB 13,4 %).
   - Основная мера генерации — RPD к `best_known`: 100 · (makespan − best) / best.
     Значение проекта на уровне — среднее RPD по его допустимым генерациям; рядом всегда
     доля допустимых (ADR 0001, ADR 0003 п. 4).
   - Дополнительно: «избежала ловушки» — доля допустимых генераций с makespan не хуже,
     чем у LFT на том же проекте; разность с LST на том же проекте.

8. **Сравнения.**
   - **Основные** — на проектах, где маршрутизатор сработал (оба окружения вместе):
     (в)−(б) и (г)−(б). Парный двусторонний Уилкоксон по проектам
     (`scipy.stats.wilcoxon`, нулевые разности отбрасываются, их число приводится),
     поправка Холма на 2 сравнения, α = 0,05. Эффект содержательный, если |средняя
     разность| ≥ δ = 0,5 п. п. (как в ADR 0003, п. 9).
   - **Дополнительные, без зачета**: (г)−(в); то же по окружениям отдельно; проекты с
     s = 0 (ложные срабатывания); вся выборка из 60 проектов — эффект политики
     маршрутизатора целиком (несработавшие проекты дают нулевую разность).
   - Справочно: где LFT, LST и лучшее правило по той же мере — ориентир «экспертного
     дерева», которое на F1 выбрало бы LFT.

9. **Чтение результата** (записано до запуска).
   - (г) ≈ (в), обе лучше (б) — модель понимает свойство, готовый вывод не нужен.
   - (в) лучше (б), (г) ≈ (б) — модель следует запрету, но из свойства вывод не делает;
     нужна экспертная разметка (дерево решений).
   - Обе ≈ (б) — описание не помогает; проверить, не выбирает ли Haiku уже LFT-подобные
     правила на (б) (тогда ловушка на (б) не срабатывает и выигрывать не у чего).

10. **Пилот** (до основного запуска, запуск `pilot-<модель>`). Цель — проверить цепочку
    (маршрутизатор → генерация → каркас → отчет), что блоки (в) и (г) доходят до модели и
    она на них реагирует, и стоимость вызова. Вывода по В2-LLM пилот не дает.
    - Проекты пилота **не входят в основную выборку**: seed 90–91, окружение × s
      {0; 0,5; 1}, n = 30, n_res = 4, `fits` — 12 проектов, 2 генерации на проект и
      уровень. Поэтому поправки после пилота не подгоняются под основные проекты.
    - Число вызовов: 12 × 2 = 24 для (б) плюс 2 × 2 × (число сработавших); при 7–8
      срабатываниях — около 55 вызовов, ≈ $0,12.
    - После пилота можно поправить только тексты блоков (п. 3) и технику (разбор ответа,
      таймауты) — с записью здесь, что и почему изменено. Выборка, порог, метрика и
      сравнения не меняются.
    - Коды уровней в файлах: `b` — (б), `v` — (в), `g` — (г).

11. **Итоги пилота `pilot-haiku` (2026-11-09) и правки** (текст (г) выше — уже исправленный).
    - **Цепочка работает.** Маршрутизатор сработал на 7 из 12 проектов (как в манифесте);
      все ответы v и g разобраны и допустимы (14/14); `fast_replies` и `repeated_replies` — 0.
      8 вызовов b упали с 403 `verification_required` (доступ организации Anthropic к Claude
      был закрыт на стороне прокси и восстановлен во время запуска), поэтому у b на
      сработавших проектах 10 допустимых из 14 (`results/pilot-haiku/report.md`).
    - **Стоимость:** Spend $0,1121 за 44 настоящих ответа (52 вызова минус 8 отказов) —
      ≈ $0,0026 за вызов. Основной запуск (680 вызовов) — **≈ $1,75**.
    - **Дефект текста (г).** Фраза «по позднему старту c срочнее h, а по позднему окончанию
      срочнее h» читается двояко. Модель поняла ее как «c срочнее h» и на всех 14 ответах
      выбрала LST или LST/LFT («критическая работа c должна получить ресурс раньше h») — то
      есть то самое проигрывающее правило. Исправление: направление задано неравенствами
      (LS_c < LS_h, LF_h < LF_c) и словами «поздний срок окончания h раньше, чем у c»;
      последствие «если поставить c раньше h …» сохранено. Названий правил по-прежнему нет.
      Версия текстов — `ROUTER_VERSION = "v2-2026-11-10"` в `src/router.py`; она пишется в
      манифест и файлы, запуск со старыми текстами продолжить нельзя.
    - **(в) не меняется.** Модель выполняет запрет (LST и MTS не берет), но переходит на GRPW,
      «TSW» или правило по ресурсоемкости — на ловушечных проектах они тоже проигрывают
      (RPD 17,6 против 6,0 у b). Это ответ на вопрос эксперимента, а не дефект текста:
      запрет без указания, что делать, уводит модель к соседнему классу правил.
    - **Дефект скрипта:** после `--retry-errors` копии b на несработавших проектах оставались
      ошибками; исправлено (копия перезаписывается из актуального b), есть тест.
    - Числа пилота в выводы В2-LLM не входят. Исправленный текст (г) проверяется повторным
      пилотом `pilot-haiku-2` на тех же 12 проектах пилота (52 вызова, ≈ $0,14).

12. **Повторный пилот `pilot-haiku-2` (2026-11-10, тексты `v2-2026-11-10`). Тексты
    зафиксированы.**
    - Все 72 генерации получены (52 вызова, ошибок нет), допустимы 14/14 на каждом уровне;
      `fast_replies` и `repeated_replies` — 0. Spend $0,1343 (разность $0,2464 − $0,1121) —
      $0,0026 за вызов; основной запуск (680 вызовов) — **≈ $1,76**.
    - На (г) модель по-прежнему выбирает LST или LST с разбором по LF в 13 ответах из 14
      (один — LFT). Неравенства она теперь пересказывает верно («у h поздний срок окончания
      раньше, LF_h < LF_c»), но делает вывод «c критическая — ставить ее раньше h», то есть
      против сказанного в описании «если поставить c раньше h, … опаздывает критический
      путь». Двусмысленности в тексте больше нет; это ответ модели на описание свойства, а не
      дефект текста. Дальнейшее уточнение (г) приблизило бы его к вердикту («ставь h
      раньше» = LFT), поэтому тексты (в) и (г) больше не меняются.
    - На (в) — снова GRPW и близкие правила по «хвосту» пути (запрет выполняется).
    - На (б) на сработавших проектах модель чаще всего пишет GRPW или «наибольший хвост
      критического пути»; LFT — в 1 ответе из 14.
    - Справочно (14 генераций на уровень, без вывода): RPD на сработавших проектах — b 8,4,
      v 15,2, g 11,3; доля «не хуже LFT» — 0,21 / 0,07 / 0,07
      (`results/pilot-haiku-2/report.md`).

13. **Основной запуск `main-haiku` (2026-11-10, тексты `v2-2026-11-10`).**
    - Ход: запуск прервался на 293 из 680 вызовов — исчерпан месячный лимит $1 ключа
      OpenRouter на стороне прокси (403 `Key limit exceeded`; Haiku и Qwen идут через один
      ключ). Научный руководитель поднял лимит, запуск продолжен тем же `--run` с
      `--retry-errors`; настройки не менялись. Итог: 899 из 900 генераций, 1 — `truncated`
      (по п. 7 ADR 0003 не перезапрашивается, считается недопустимой); `fast_replies` и
      `repeated_replies` — 0. Spend всего запуска — **$1,77** ($2,0132 − $0,2464).
    - Маршрутизатор сработал на 38 из 60 проектов; ложных срабатываний при s = 0 — 4 (все
      в `shared`).
    - **Основные сравнения** (38 сработавших проектов, Уилкоксон, Холм на 2;
      `results/main-haiku/eval.md`):
      - (в)−(б): +8,70 п. п. (медиана +6,99), (в) хуже на 36 проектах из 38,
        p(Холм) = 1,5·10⁻¹⁰ — **вердикт ухудшает результат**;
      - (г)−(б): −1,06 п. п. (медиана −0,19), лучше/хуже/равно — 22/13/3, p(Холм) = 0,072 —
        **значимого различия нет**.
    - Дополнительно, без зачета: (г)−(в) −9,77 п. п. (p = 1,6·10⁻⁷); в `isolated` (г)−(б)
      −2,54 п. п. (p = 0,011, без поправки), в `shared` +0,42 (p = 0,86). Правило LFT на
      тех же 38 проектах — средний RPD 2,40 против 9,63 (б), 18,33 (в), 8,57 (г); доля
      генераций не хуже LFT — 0,17 / 0,11 / 0,31.
    - Что выбирает модель (по названию метода в ответе, грубая классификация по ключевым
      словам, сработавшие проекты): (б) — GRPW или «наибольший хвост пути» в 164 из 190,
      LFT в 11; (в) — GRPW-подобные в 171 из 190, LFT в 1; (г) — LST в 118, LST с разбором по
      LFT в 53, LFT в 15 из 189.
    - Чтение по п. 9: ни один исход из записанных точно не подходит. Вердикт-запрет
      уводит модель к GRPW, который на F1 проигрывает сильнее; описание свойства модель
      понимает как довод за LST, а значимого выигрыша над (б) нет. Простое правило LFT
      лучше всех трех уровней — это аргумент за экспертную подсказку (что брать, а не
      только что не брать) или дерево решений, о котором говорил руководитель.

14. **Повтор на второй модели — Qwen** (записано 2026-11-10, до генерации).
    - Цель — проверить, **повторяются ли выводы п. 13** на другой модели: (в) хуже (б),
      (г) не лучше (б), LFT лучше всех уровней. Прямого вывода «какая модель лучше» нет:

15. **Первая попытка `pilot-qwen` (2026-11-10) и ограничение рассуждения Qwen** (правка
    техники по п. 14, тексты и выборка не меняются).
    - С настройками по умолчанию Qwen тратил весь `max_tokens` = 16000 на скрытое
      рассуждение: в 8 первых ответах `reasoning` = 16000, текст ответа пустой, статус
      `truncated`, 205–236 с на вызов. Запуск остановлен; эти вызовы оплачиваются
      (16000 токенов вывода каждый). У Haiku рассуждение занимало около 4 тыс. токенов
      (ADR 0003, п. 7).
    - Пробы на настоящем промпте пилота (проект `F1_isolated_n30_r4_s0.0_fits_seed90`,
      уровень b, 2026-11-10): `reasoning_effort = "low"` (параметр OpenAI, запуск
      `probe-qwen`, `--limit 1`) и `reasoning: {"effort": "low"}` — прокси или OpenRouter их не
      применяют, снова 16000 токенов рассуждения и `truncated` (237 и 271 с);
      `reasoning: {"max_tokens": 4000}` — рассуждение 1092 токена, ответ разобран, 33 с;
      `reasoning: {"enabled": false}` — без рассуждения, ответ разобран, 56 с.
    - Решение: лимит рассуждения **4000 токенов** — порядок рассуждения Haiku (около 4 тыс.,
      ADR 0003, п. 7); отключать рассуждение совсем не стали, чтобы условия моделей были
      ближе. Параметр `--reasoning-max-tokens` в `llm_generate.py` добавляет в тело запроса
      `reasoning: {"max_tokens": N}`; без параметра запрос прежний (Haiku не затронут).
      Значение пишется в манифест и в файлы; продолжить запуск с другим значением нельзя.
      Это настройка модели, а модель — фиксированный фактор: на сравнение уровней внутри
      запуска Qwen она не влияет, при описательном сопоставлении с Haiku указывается.
    - Папка первой попытки `pilot-qwen` (9 файлов `truncated`) удаляется, пилот запускается
      заново с `--reasoning-max-tokens 4000`. `probe-qwen` в отчеты не входит.

## Последствия

- Изменение порога, текстов блоков, выборки или метрики после первого вызова LLM —
  только новой записью здесь и новым запуском.
- Результат — `experiments/v2_counterexamples/results/<run>/`; сырые ответы — в
  `generations/`, вне git (как в В1).
- Ограничения, которые войдут в отчет: эталон не оптимум (см. п. 7); одна модель
  (Haiku); одна ловушка (F1) и одна характеристика; выборка — синтетика одного генератора.
  Порог маршрутизатора подобран на проектах одного генератора (сетка F1) и на проектах
  другого происхождения не проверен: новые seed проверяют схему «маршрутизатор + LLM» на
  проектах того же устройства, но не перенос порога. Уже видно, что перенос не
  гарантирован: на PSPLIB триггер сработал на 1 инстансе из 108, и MTS там не проиграл
  (precision 0,00, `triggers.md`); при общем ресурсе точность ниже (BA 0,66 против 0,99
  на n = 120). Проверить порог на других наборах — после обзора наборов данных.
