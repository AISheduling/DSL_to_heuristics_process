# Кандидатные научные вопросы (этап 0)

Шаблон — ТЗ, прил. Б; опора — `maps.md`, `prior_work_overlap.md`, карточки ядра.
В первую очередь — направления (встреча 08.10.2026): (1) метаданные проекта в онлайн-генерации; (2) гранулярность.

**Общие условия для всех вопросов**

- **Предусловие (issue #1):** независимый чекер расписаний (предшествование, ресурсы, makespan) и интерпретируемые числа качества. Без этого ни один вопрос не выполним.
- **Основная метрика (выбрана заранее):** среднее отклонение makespan от эталона — ARPD, % (BKS / оптимум для J30; лучшие известные решения PSPLIB для J60–J120).
- **Единица бюджета:** число построенных расписаний на инстанс (как в luo2022gprcpsp и kim2026vlcea). Вызовы LLM и токены считаются отдельно и сравниваются только внутри одной модели (ТЗ, разд. 7).
- **Минимальный интересный эффект δ** фиксируется до эксперимента. Предварительный ориентир — разница GP1 и лучшего одиночного правила в luo2022gprcpsp: AvgDevLB на J30 2,86 % против 3,32 %, т. е. ≈0,5 п.п.
- **Статистика:** несколько генераций на инстанс (≥5), парный Уилкоксон по инстансам, поправка Холма на число сравнений.
- **Данные:** PSPLIB J30 — отладка, J60 / J120 — тест; индикаторы проекта — как в guo2021prselection (12 индикаторов, есть в RCPLIB). Весенние данные (5 постановок по одному инстансу) для этих вопросов не подходят.
- **Схема генерации расписания:** стандартная SSGS, как у baselines (GP1, Luo 2026). Текущий цикл `run_schedule` не является SSGS: работы стартуют только в текущий момент и не вставляются раньше.
- **Метаданные:** текущий DSL содержит только сетевые характеристики графа (`calculate_metrics.py`); ресурсных индикаторов нет, OS и CPL считаются не по стандартным формулам (OS делится на n(n−1), CPL — число узлов, а не длительность). Для сравнения с guo2021prselection их нужно привести к стандартным.
- Размеры выборок ниже — предварительные и пересчитываются после первого прогона.

**Порядок приоритета:** В1 и В2 — направление (1); В3 — направление (2); В4 — сопутствующий (карта 3).

## В1. Генерация кода под инстанс против офлайн-правила с теми же метаданными (направление 1)

| Поле | Содержание |
| --- | --- |
| Вопрос | Даёт ли однократная LLM-генерация кода приоритета под конкретный проект по его метаданным выигрыш по ARPD относительно офлайн-правила, использующего те же индикаторы проекта, при равном числе построенных расписаний (1 SSGS на инстанс) на PSPLIB J60 / J120, и при каких значениях индикаторов (RS, RF, OS) выигрыш исчезает? |
| Гипотеза | Генерация под инстанс снижает ARPD не менее чем на δ относительно GP1 только на подмножестве проектов с высокой ресурсной напряжённостью (низкий RS); в среднем по набору выигрыша нет. |
| Что варьируется | Источник эвристики (4 уровня): (а) LLM-генерация под инстанс с метаданными в промпте; (б) та же генерация без метаданных — только описание задачи; (в) офлайн-правило GP1; (г) выбор правила под проект — J48-MC или LLM-выбор из 36 известных правил по тем же метаданным. |
| Что фиксируется | Каркас SSGS и интерфейс функции; модель и температура; формат промпта (одно представление); набор инстансов; 1 расписание на инстанс; число генераций на инстанс. |
| Основная метрика и равенство бюджета | ARPD; бюджет — одно построенное расписание на инстанс для всех уровней. Стоимость LLM (вызовы, токены) — отдельной строкой: у (а) и (б) один вызов на инстанс, у (в) ноль при применении. |
| Клетка карты | Карта 1: online-генерация под инстанс × одна функция приоритета. Пуста для кода на RCPSP («не дошли»), с оговоркой про выборку из 10 работ. |
| Ближайший аналог | luo2026llmrcpsp — индикаторы проекта как входы офлайн-правила, найденного LLM-поиском; мы проверяем, даёт ли что-то генерация под каждый проект сверх такого правила. |
| Baseline из пласта C | GP1 из luo2022gprcpsp (формула в ур. 3, применяется без обучения); J48-MC из guo2021prselection (12 индикаторов, 1 правило на инстанс). |
| Baseline из пласта A/B | Правило уровня luo2026llmrcpsp (промпты и валидация в ancillary-файле; переимплементация — по возможности); минимум — уровень (б), та же LLM без метаданных. |
| Что аналог уже сказал | luo2026llmrcpsp: индикаторы проекта во входах правила полезны (контрфактически, §6.1). guo2021prselection: выбор правила по индикаторам даёт маргинальный выигрыш, когда сильное правило доминирует. kim2026vlcea: однократный вызов LLM на инстанс не показал выигрыша над ручным ремонтом (с LLM-данными, не кодом). |
| Результат, который нас не устроил бы, но был бы честным | (а) ≈ (в): генерация под инстанс не лучше одного офлайн-правила, т. е. метаданные проекта уже «упакованы» в офлайн-правило, а вызов LLM на каждый проект не окупается. |
| Отрицательный результат | Публикуем как отрицательный: для статического RCPSP адаптация под проект через генерацию кода не превосходит офлайн-правило и селектор при равном числе расписаний. |
| Выполнимость | С доработкой: чекер (issue #1), передача 12 индикаторов в промпт, реализация GP1 и J48-MC (данные RCPLIB). Порядок объёма: 2 LLM-уровня × ~100 инстансов × 5 генераций ≈ 1 000 вызовов — один эксперимент за семестр выполним. |

## В3. Гранулярность генерируемого кода (направление 2)

| Поле | Содержание |
| --- | --- |
| Вопрос | Даёт ли расширение генерируемого интерфейса с одной функции приоритета до двух функций (`select_job_fn` + `allocate_fn`) или до полного решателя выигрыш по ARPD относительно одной функции при фиксированном представлении задачи и равном числе расписаний на J60, и на каких проектах выигрыш исчезает? |
| Гипотеза | Две функции снижают ARPD не менее чем на δ относительно одной функции приоритета только при ресурсно-напряжённых проектах; полный решатель хуже обеих по доле валидных генераций и не лучше по ARPD. |
| Что варьируется | Гранулярность (3 уровня): одна функция приоритета (allocate — стандартный шаг SSGS); две функции; полный решатель. |
| Что фиксируется | Представление задачи (одно и то же описание для всех уровней), модель, температура, метаданные, инстансы, число генераций, 1 расписание на инстанс, независимый чекер. |
| Основная метрика и равенство бюджета | ARPD по валидным генерациям; вторичная — доля валидных генераций (невалидная → штраф или подстановка baseline, правило фиксируется заранее). Бюджет — 1 вызов и 1 расписание на инстанс; выходные токены — отдельно. |
| Клетка карты | Отдельной оси в картах ТЗ нет; фактор внутри клетки «одна функция приоритета» карты 1. Ни одна из 10 работ гранулярность не сравнивает. |
| Ближайший аналог | ye2024reevo — два оператора GA эволюционируют по очереди, но без сравнения с одним; luo2026llmrcpsp — выразительность одной функции повышается «гейтами», а не разбиением. |
| Baseline из пласта C | GP1 (luo2022gprcpsp) и лучшее одиночное правило (LFT / LST) в том же SSGS. |
| Baseline из пласта A/B | Уровень «одна функция приоритета» с интерфейсом как у luo2026llmrcpsp (`priority_score`). |
| Что аналог уже сказал | Прямо — ничего в ядре; до финальной формулировки прочитать zhao2026glns (G-LNS, пара связанных функций), chen2026a2dept и zhu2026simpleevol — по аннотациям они касаются гранулярности. Наши весенние данные: две функции короче по токенам, чем полный решатель; доли падений посчитаны с разными определениями и знаменателями, качество не измерено, представление смешано с гранулярностью (`prior_work_overlap.md`, п. 1.3). |
| Результат, который нас не устроил бы, но был бы честным | Две функции не лучше одной функции приоритета: второй интерфейс `allocate_fn` не используется или повторяет стандартный шаг SSGS. |
| Отрицательный результат | Публикуем: для однократной генерации на RCPSP достаточно узкого интерфейса (одна функция приоритета); разбиение на две не даёт выигрыша. |
| Выполнимость | С доработкой. В текущем каркасе в базовом RCPSP `allocate_fn` может только вернуть требуемые ресурсы, задержать работу или нарушить ограничения — уровень «две функции» вырождается в «приоритет + решение ждать». До эксперимента нужно переопределить уровни (варианты: набор генерируемых решений «приоритет → приоритет + политика ожидания → полный решатель»; или multi-mode, где `allocate_fn` выбирает режим) — решить на встрече; привести три уровня к одному представлению. Порядок объёма: 3 уровня × ~100 инстансов × 5 ≈ 1 500 вызовов. Выполним за семестр. |
