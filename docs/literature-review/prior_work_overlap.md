# Что из нашего задела уже сделано другими и лучше (этап 0)

Источник: карточки ядра (`cards/`), `review_table.csv`, `maps.md`. Требование ТЗ — разд. 5, п. 4: по пунктам, без смягчений.

**Наш задел:** каркас `scheduler_skeleton.py` с двумя заполняемыми функциями `select_job_fn` / `allocate_fn`; три представления задачи — Text, DSL, Skeleton; весной однократные генерации под инстанс по DSL-описанию и сетевым метаданным графа (`calculate_metrics.py`), без поиска. Данные — 5 постановок семейства RCPSP по одному инстансу (стандартный RCPSP — только PSPLIB j301_1; остальные — одна машина со штрафами, невозобновляемые ресурсы, условные предшествования, мультипроект).
- **Подтверждено:** Skeleton требует в 2–3 раза меньше выходных токенов (3059 → 2950 → 1257).
- **Частично:** «Skeleton реже падает». Код исполнялся во всех трёх подходах (`run_heuristics_text.py`, `run_heuristics_dsl.py`, `run_heuristics_skeleton.py`), но «падение» определено по-разному: для полного решателя — исключение или таймаут 30 с, а запуски с ошибкой генерации **не попадают в знаменатель**; для Skeleton — ошибка компиляции или выполнения без таймаута, а ошибки генерации **учитываются** (`skipped_generation_error`). Сравнение долей без пересчёта на общий знаменатель некорректно.
- **Не подтверждено:** корректность через каркас (опровергается кодом, см. 1.6); качество расписаний (независимого чекера нет; числа версии d3dadbc6 не интерпретируемы, issue #1).

**Что генерирует каждый подход:** Text и DSL — полный решатель (`solve_scheduling(jobs, resources)`); Skeleton — две функции в каркасе.

### 1.2. Две функции вместо одной (гранулярность)
- **Кто уже сделал:** никто из 10 работ ядра не сравнивает одну функцию с несколькими. Ближе всего ye2024reevo: два оператора GA эволюционируют **по очереди**, без сравнения гранулярности. **Не прочитаны, но по аннотациям близки:** zhao2026glns (G-LNS — пара связанных функций), chen2026a2dept (алгоритм целиком), zhu2026simpleevol (меньше каркаса — лучше с сильной LLM). Пока они не прочитаны, вывод «никто не сравнивал» держится только на ядре.
- **Что у нас остаётся:** вопрос по направлению (2). Сейчас это свойство интерфейса, а не результат: гранулярность в весенних запусках не варьировалась отдельно от представления (см. 1.3). Кроме того, в текущем каркасе у `allocate_fn` в базовом RCPSP нет допустимой свободы: работа стартует в текущий момент, длительность от выделения не зависит, поэтому `allocate_fn` может только вернуть требуемые ресурсы, задержать работу (запросив больше доступного) или нарушить ограничения (см. 1.6). Уровень «две функции» в нынешнем виде вырождается в «приоритет + решение ждать»; его нужно переопределить до эксперимента.

Но в весенних данных **представление смешано с тем, что генерируется**: Text и DSL дают полный решатель, Skeleton — две функции. Поэтому вклад представления из этих данных не выделяется. Та же ошибка смешения, которую мы отмечаем у ReEvo и MCTS-AHD.

### 1.4. Экономия токенов (3059 → 2950 → 1257)

### 1.5. Надёжность генерации («реже падает»)
- **Кто уже сделал и лучше:**

- **Что у нас остаётся:** доля падений по подходам — вспомогательная метрика, не вклад. Её сравнение между Text / DSL / Skeleton смешано с тем, что генерируется (см. 1.3), и посчитано с разными определениями падения и разными знаменателями (см. «Частично» выше). Статус OK ничего не говорит о допустимости расписания: у полного решателя makespan извлекается из произвольного вывода функции по эвристике ключей (`extract_objective`), проверки расписания нет; у Skeleton OK не исключает молчаливую подмену невалидного `job_id`, обход ресурсов через `allocate_fn` и неполное расписание.

### 1.6. Корректность через каркас
- **Кто уже сделал и лучше:** у всех работ ядра допустимость обеспечивает хозяин-алгоритм (SGS, GLS, среда). Лучше всех в этом отношении romeraparedes2024funsearch: решение проверяет **отдельный** `evaluate`, а не сам каркас. Независимого чекера расписаний нет ни у одной работы по RCPSP (luo2026llmrcpsp, kim2026vlcea, tian2026gpguidedllm).
- **Что у нас остаётся:** ничего как вклад. Утверждение **опровергается кодом**: предшествование каркас гарантирует (`is_eligible`), а ресурсные ограничения — нет. Если `allocate_fn` вернёт меньше требуемого, ресурсы списываются по возвращённому значению, а освобождаются по требуемому, и расписание нарушает мощности без ошибки. При тупике цикл прерывается, а makespan считается по неполному расписанию. Независимый чекер — предусловие любого эксперимента, а не результат (issue #1).

### 1.7. Генерация под инстанс по описанию и метаданным
- **Кто уже сделал рядом:**
  - kim2026vlcea — один вызов LLM на инстанс до поиска, но генерирует **данные** (оценки работ), а не код; сравнения с оценками без LLM нет; лучший вариант не отличим от ручного ремонта HC;
  - luo2026llmrcpsp — индикаторы проекта как **входы офлайн-правила**, их вклад подтверждён контрфактически (§6.1, табл. 18);
  - guo2021prselection, luo2022gprcpsp (CHAID) — выбор готовых правил под проект по индикаторам, без LLM;
  - tian2026gpguidedllm — признаки инстанса в контексте LLM, но LLM принимает решения, а не пишет код.
- **Не прочитаны, но по аннотациям близки:** zhang2025instspechh (генерация под подкласс инстансов, не на планировании), Sartori et al. 2025 (LLM генерирует смещение BRKGA по метрикам инстанса).
- **Что у нас остаётся:** генерация **кода** под инстанс по метаданным на RCPSP в выборке не встречается (карта 1, клетка «online × одна функция приоритета»). Это ядро направления (1), но только при сравнении с офлайн-правилом, параметризованным теми же метаданными (Luo 2026 / GP1), и с селектором правил (J48-MC). Без такого сравнения пустота клетки ничего не доказывает.

### 1.8. Однократная генерация без поиска
- **Кто уже сделал и лучше:** все работы пласта A и luo2026llmrcpsp используют поиск (популяция, MCTS, острова) с сотнями и тысячами оценок. Наша схема соответствует только шагу инициализации (I1 в EoH). Ближайший ориентир — абляция A1 в luo2026llmrcpsp, но это офлайн-отбор лучшего из ≈1058 независимых генераций, а не одна генерация.
- **Что у нас остаётся:** по поиску мы слабее, а не «иначе». Однократная генерация может быть осознанным режимом (дёшево, под инстанс) только при сравнении с поиском и классическими baselines при равном бюджете.
