| 1. Класс задачи | Экстремальная комбинаторика (cap set, admissible sets; в SI — ёмкость Шеннона циклических графов, corners problem) и онлайн одномерная упаковка в контейнеры. Задач планирования нет | разделы «Extremal combinatorics», «Bin packing»; SI B |
| 2. Режим использования | Смешанный. Bin packing: offline-поиск переиспользуемой эвристики (обучение → выбор по валидации → тест), при применении LLM не нужна. Комбинаторика: поиск программы под конкретные входы (значения n), программа — компактное представление решения, переноса на новые инстансы не проверяют | «Bin packing»; SI E.4; «Specification», «Evaluation» |
| 3. Что генерируется | Одна функция внутри фиксированного скелета: `priority` (комбинаторика) или `heuristic` (bin packing). Абляция «W/O Skeleton»: генерация программы, которая сразу выдаёт упорядоченный список всех векторов | «Specification», рис. 2; SI A.1 |
| 4. Интерфейс с ядром | Скелет с одной заполняемой функцией (декоратор `@funsearch.evolve`) + фиксированный, написанный человеком `evaluate`; программа целиком запускается в песочнице | рис. 2; SI C, F.2 |
| 5. Контекст, который видит модель | Шаблон спецификации (импорты, докстринги) + k = 2 предыдущих версии функции из одного острова, упорядоченные по возрастанию оценки (`priority_v0`, `priority_v1`), + пустой заголовок `priority_v2`. Функции скелета, стоящие перед `priority_v0` (в т. ч. `solve`), из промпта удаляются. Числовые оценки, трассы, описание задачи вне докстрингов в промпт не передаются — только порядок версий. Пользователь может добавить знания о задаче в спецификацию. Retrieval нет | «Prompt»; Methods «Prompt building»; Extended Data Fig. 1 |
| 6. Кто выбирает контекст | Фиксированный алгоритм: случайный остров → больцмановский выбор кластера по оценке (температура падает по расписанию) → программа внутри кластера с предпочтением коротких. Ни человек по ходу поиска, ни LLM не выбирают | Methods «Evolutionary method…», ур. (1); SI F.3 |
| 7. Механизм поиска | Островная эволюция: 10 островов, каждые 4 ч худшая половина сбрасывается и засевается лучшей программой выживших; внутри острова — кластеры по «сигнатуре» (вектору оценок по входам). Асинхронная распределённая система: 15 сэмплеров, ≈140–150 оценщиков, 4 сэмпла на промпт | Methods; SI A.5, E.1 (табл. E.2), F |
| 8. Модели | Codey (на базе PaLM 2, размер не указан) — основная; StarCoder 15B — сравнение. Температура 1,0, top-p 0,95. Одна модель на прогон, маршрутизации нет | «Pretrained LLM»; SI A.2, E.1 |
| 9. Baselines | Комбинаторика: лучшие известные конструкции из литературы; CP-SAT (с ручными ограничениями и без) для admissible sets. Bin packing: first fit и best fit. Без LLM: эволюция со случайными AST-мутациями. Абляции: без скелета, без эволюции, один остров, k = 1. GP-гиперэвристики для bin packing упомянуты в related work, но экспериментально не сравниваются | табл. 1; SI A.1, A.2, A.4; Methods «Related work» |
| 10. Данные | Bin packing: OR-Library OR1–OR4 (по 20 инстансов, 120–1 000 предметов); обучение на 20 сгенерированных инстансах размера OR1, валидация на 20 инстансах размера OR2, тест на OR1–OR4. Weibull: обучение и валидация по 5 инстансов × 5 000, тест 5k / 10k / 100k. Перенос по размеру есть, между распределениями — нет. Комбинаторика: входы — значения n (и w) | SI E.4; «Bin packing»; табл. 1 |
| 11. Корректность | Решение проверяется написанной человеком функцией `evaluate` (например, `is_capset`, `is_valid_packing`), отдельной от эволюционируемого кода; выполнение — в песочнице с таймаутом и лимитом памяти (по умолчанию 30 с, 2 ГБ); ошибочные, зависшие и невалидные программы отбрасываются; программы, вызывающие предыдущие версии, исключаются. Входят ли отброшенные в счёт «programs generated» — явно не сказано | «Evaluation»; SI E.1, F.2 (алг. F.5) |
| 12. Стоимость | Бюджет — число сгенерированных программ: порядка 10⁶ на результат, ≈2 млн для I(15, 10). Оценка стоимости для воспроизведения на StarCoder: 800–1 400 USD и 250–500 кВт·ч за 2 млн сэмплов (15 GPU A100 + 5 CPU-серверов, 2 дня). Токены не считаются. Сравнение со случайными мутациями — по числу программ; с CP-SAT бюджет не уравнен (≥50 ч × 1 024 параллельных запуска). «Стоимость при равном качестве» не оценивается | «Pretrained LLM»; SI A.1, A.4, A.5 |
| 13. Статистика | Абляции и сравнение LLM: по 5 прогонов, стандартные ошибки на графиках. Повторяемость: cap set n = 8 — 4 успешных из 140 запусков; admissible sets — по 5 прогонов; bin packing (Weibull 10k) — 10 прогонов, 0,44 % ± 0,11 % (тип разброса не указан). Статистических тестов нет | SI A.1–A.3; Methods «Robustness» |
| 14. Воспроизводимость | Код эволюционного алгоритма и однопоточный пайплайн опубликованы (GitHub + архив SI), но без LLM и песочницы (заглушки `NotImplementedError`); найденные функции и ноутбуки для пересчёта bin packing есть; структура промпта описана. Пригодность как baseline: да, при подключении своей LLM и песочницы | «Code availability»; README архива; `implementation/sampler.py`, `evaluator.py` |
| 15. Результат и ограничения | Скелет + эволюция одной функции с помощью LLM дают новые результаты: cap set размера 512 в n = 8 и нижнюю границу ёмкости 2,2202; эвристики bin packing лучше first fit и best fit на всех наборах. Ограничения: нет задач планирования; в bin packing сравнение только с first fit и best fit; бюджет ≈10⁶ программ несопоставим с LLM-AHD-работами с бюджетом ~10³; лучшие результаты по комбинаторике получены с участием человека (найденная симметрия → новый скелет); сами авторы ограничивают применимость задачами с быстрым оценщиком, «богатой» оценкой и выделяемой частью для эволюции | «Admissible sets»; табл. 1; «Discussion»; SI E.3 |
| Чем отличаемся от этой работы | Сходство: как и FunSearch, генерируем код внутри фиксированного программного скелета (`scheduler_skeleton.py`); остальной код и оценка неизменны. По механизму «скелет + заполняемая функция» не отличаемся.<br>Отличия: (1) две заполняемые функции (`select_job_fn`, `allocate_fn`) вместо одной `priority`; (2) нет эволюционного поиска — независимые однократные генерации (3 подхода × 5 инстансов × 10), а не популяция с отбором и ≈10⁶ программ; (3) домен — RCPSP и SSGS; (4) варьируется представление задачи (текст / DSL / Skeleton). Отличие (1) как научный вклад пока не обосновано | — |
