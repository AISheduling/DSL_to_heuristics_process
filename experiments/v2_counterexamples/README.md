# В2: проверка инварианта ловушки F1

Здесь проверяется утверждение: правило LST (и MTS) проигрывает тогда и только тогда, когда в
проекте есть свойство ловушки F1 «ресурсно-слепой резерв» (описание и пример:
`src/generators/traps/resource_blind_slack.md`). Три скрипта запускаются по порядку:

```
python experiments/v2_counterexamples/make_instances.py [--seeds 20] [--out instances.json]
python experiments/v2_counterexamples/run_rules.py --run R [--samples 100] [--workers 8]
python experiments/v2_counterexamples/run_rules.py --run R --psplib
python experiments/v2_counterexamples/check_invariants.py --run R
python experiments/v2_counterexamples/fit_triggers.py --run R [--no-psplib]
```

## `make_instances.py` — сетка проектов

Пишет манифест `instances.json`: параметры каждого проекта и хэш его содержимого.

Сетка: окружение (`isolated` — отдельный ресурс ловушки, `shared` — общий с фоном) × n ∈ {30, 60,
120} × n_res ∈ {2, 4} × s ∈ {0, 0.25, 0.5, 0.75, 1} × вид контроля (`fits`, `short_delay`) ×
seed. При s = 1 все блоки — ловушки и вид контроля ни на что не влияет, поэтому такой проект один
(control `fits`); в анализе он входит в оба вида контроля. При 20 seed — 2160 проектов.

Сами проекты на диск не пишутся: генератор детерминирован, проект восстанавливается по
параметрам за миллисекунды. Хэш нужен, чтобы изменение генератора не прошло незамеченным
(`run_rules.py` сверяет его), и для кэша результатов.

## `run_rules.py` — прогон правил

**Сетка** (по `instances.json`). Для каждого проекта:
- пять правил RULES_V2 (LFT, LST, MTS, GRPW, GP1) в SSGS, makespan из независимого чекера;
- эталон `best_known` (правила в SSGS и PSGS плюс `--samples` проходов сэмплирования) и LB;
- опоздание цепочки ловушки у каждого правила и неизбежная задержка (сумма длительностей h,
  которые не помещаются рядом со своей работой цепочки);
- 12 индикаторов guo2021.

Пишет `results/R/instances.csv` (строка на проект) и `results/R/rules.csv` (строка на
«проект × правило»). Проекты, уже посчитанные с тем же хэшем, пропускаются. `--workers 1` —
без пула процессов.

**`--psplib`.** Те же правила на 108 инстансах выборки В1 (`experiments/v1_pilot/sample.json`),
эталон — BKS. Пишет `results/R/psplib_rules.csv`.

Основная мера — `gap_vs_others`: на сколько процентов makespan правила хуже лучшего из остальных
правил на том же проекте. Эталон для неё не нужен. `rpd_best` — отклонение от `best_known`.

## `check_invariants.py` — критерии

Пишет `results/R/invariants.md` (отчёт для чтения) и `results/R/invariants.json`.

Критерии зафиксированы до первого прогона сетки. Ячейка — (окружение, n, n_res); для каждого
целевого правила R (LST, MTS) в каждой ячейке:

| | Критерий | Как проверяется |
|---|---|---|
| C1 | Проигрыш заметный | медиана `gap_vs_others(R)` при s ≥ 0.5 не меньше 5 п. п. |
| C2 | Проигрывает именно R | R хуже защищённого правила LFT: парный Уилкоксон по `rpd_best` на проектах с s ≥ 0.5, средняя разность > 0, p по Холму < 0.05 |
| C3 | Доза — ответ | Спирмен(s, `gap_vs_others(R)`) > 0, p по Холму < 0.05, при каждом виде контроля (проекты этого контроля плюс проекты с s = 1) |
| C4 | Контроль чистый | при s = 0 медиана `gap_vs_others(R)` меньше 1 п. п. при каждом виде контроля |

Поправка Холма делается по всем проверкам C2 и C3 отчёта сразу. Ячейка подтверждена, если
выполнены все четыре критерия.

Справочно, без зачёта: проигрыш правил на PSPLIB, доля проектов, где цепочка опоздала сверх
неизбежного, и качество эталона (доля доказанных оптимумов, разрыв с LB).

## `fit_triggers.py` — пороги метахарактеристик

Пишет `results/R/triggers.md` (отчёт), `results/R/triggers.json` (правило → признак, направление,
порог, объяснение для маршрутизатора), `results/R/triggers_report.json` (все числа) и кэш
признаков `results/R/features.csv` по хэшу проекта.

- Признаки — `src/rule_features.py` и 12 индикаторов
  guo2021 из `instances.csv`.
- Метка: правило (LST, MTS) проиграло, если его makespan хуже лучшего из остальных правил на
  5 п. п. и больше.
- Для каждого признака подбирается порог с направлением (решающий пень), лучший по
  сбалансированной точности на проектах n = 30 и 60 обоих окружений. Триггер правила —
  метахарактеристика с лучшей точностью на обучении; проверочные данные в выбор не входят.
- Проверка: n = 120 отдельно по окружениям и 108 инстансов PSPLIB (если есть `psplib_rules.csv`).

## Сокращения

- **BKS** — Best Known Solution — лучшее известное решение инстанса из литературы.
- **BA** — сбалансированная точность: среднее долей верно угаданных проигрышей и не-проигрышей.
- **CSV** — текстовая таблица с разделителем-запятой.
- **GP1** — правило приоритета из статьи Luo et al. (2022), найденное генетическим программированием.
- **GRPW** — Greatest Rank Positional Weight — первой ставится работа с наибольшей суммой своей длительности и длительностей прямых преемников.
- **LB** — Lower Bound — нижняя граница makespan.
- **LFT** — Latest Finish Time — первой ставится работа с самым ранним поздним сроком окончания.
- **LST** — Latest Start Time — первой ставится работа с самым ранним поздним стартом.
- **MTS** — Most Total Successors — первой ставится работа с наибольшим числом всех последующих работ.
- **PSGS** — Parallel Schedule Generation Scheme — параллельная схема построения расписания.
- **PSPLIB** — Project Scheduling Problem Library — стандартная библиотека тестовых проектов RCPSP.
- **RCPSP** — Resource-Constrained Project Scheduling Problem — задача календарного планирования проекта с ограниченными ресурсами.
- **SSGS** — Serial Schedule Generation Scheme — последовательная схема построения расписания (каркас проекта).
- **п. п.** — процентные пункты.
